## Context

Requirement 21 of the product requirements document asks for a toil agent. That document is not in this tree; `docs/specs/` is gitignored and the bean body carries the contract. A labelled Jira ticket becomes one pull request, linked back onto the ticket, with no person in the loop.

ADR 074 had already settled the workflow format. A file is read and never evaluated, it holds no condition, and a capability that wants a condition belongs in Rust. `WorkflowCapability` existed under that rule, and nothing reached it from a command line.

Two questions were left. Where does the judgement "is this work fiddle takes on?" live. And what does the workflow document have to gain before it can carry the toil route at all.

This record grades each claim it makes. MEASURED means a test in this repository observes the behaviour. ARGUED means the claim is read off the source and no test fails if it is wrong. OBSERVED means a person ran it once against real infrastructure and recorded what happened, and no test in this repository reproduces that run. STILL NOT REACHED means no run has done the thing.

Every toil measurement below runs the compiled binary against a loopback model gateway, a loopback Jira server, a compiled stand-in for `gh`, and a local bare git repository as the remote. One toil run has since reached real infrastructure, and the Consequences record what it found: a real Jira site and a real model gateway on 2026-09-03, and no forge.

ARGUED, read off ADR 074 and off the source at `77b82f6`: the context above. No test asserts what ADR 074 settled, and none asserts that nothing reached `WorkflowCapability` from a command line before this milestone.

## Decision

**Eligibility is an outer Rust gate. It is not a step.**

ARGUED, read off the source at `77b82f6`: `toil::qualify` runs in `crates/fiddle-cli/src/main.rs`, in `qualified`, after `selected_workflow` loads the document and before the workflow runs. `RULES` holds the thirteen rule names the gate applies: twelve in `toil::qualify` and the thirteenth in `toil::recheck`. It answers `Qualification::Eligible` or `Qualification::Refused`, and a `Refusal` carries the rule that failed, what was found and the remedy that would change the answer. That order has a cost. ARGUED, read off the same source: a deployment whose toil document is malformed refuses before the ticket is qualified. So the ticket receives a document error rather than a refusal comment on its own issue, and the person who filed it is told nothing. No test drives a `jira:` toil run against a malformed document.

Three reasons hold the gate outside the document. That placement, all three reasons, and the three paragraphs that state them are ARGUED, read off the source at `77b82f6` and off ADR 074, except where a sentence names its own measurement. ADR 074 gives the first. Eligibility is nothing but conditions, and a condition in a file means the capability belongs in Rust.

The second is cost. An ineligible ticket must pay for no worktree, no forge client and no model call. Placing the judgement inside the document would spend all three to reach the step that declines the work. MEASURED: `a_refused_ticket_is_told_why_on_its_own_issue` in `crates/fiddle-acceptance/tests/toil.rs` counts zero model calls, zero pull requests and zero branches for a ticket without the trigger label, and the run exits 2.

That reason had a sibling cost this record did not name, and `fiddle-ihl1` removed it rather than recording it. `qualified` used to resolve `config.agent` and call `model_client`, which resolves the model credential, before it observed the ticket and before `toil::qualify` ran. So a deployment that configured no `[agent]` table answered a label-less ticket with `fiddle::config::capability_unconfigured`, naming a deployment fault the person who filed the ticket cannot act on, and never reaching the rule that would have told them what to do. `toil::qualify` now applies its twelve rules in two halves. `toil::deterministic` applies the nine that read the tracker's own fields and needs no model. `toil::review_of` applies the three the ambiguity review decides, and `qualified` resolves `[agent]` and the model credential only when the nine have held. `toil::qualify` is the two called in order, so no caller of the whole gate changed. Nine plus three is twelve, and `RULES` holds thirteen. The thirteenth is `TICKET_HELD_ITS_REVISION`, and it is in neither half. `toil::recheck` applies it against the revision the run observes, which the section below records. MEASURED through the binary: `a_ticket_the_deterministic_rules_refuse_is_refused_on_a_deployment_that_configured_no_model` drives a label-less ticket against a document with no `[agent]` table and requires the refusal, the comment on the ticket and exit 2 rather than the configuration error. Its pair, `a_ticket_the_deterministic_rules_admit_still_needs_the_agent_table`, drives an eligible ticket against the same document and requires the configuration error, so the first is about which rule failed and not about this build having stopped resolving `[agent]`.

The third is the refusal itself. A refusal is a write on the ticket, and the run that must not start cannot be the run that performs it. So the gate publishes the refusal, and the document never sees the ticket. ADR 084 records what that required of the effect executor.

**A qualification is rechecked against the revision the run observes.**

ARGUED, read off the source at `77b82f6`: `toil::recheck` compares the `fields.updated` the ticket was qualified at with the revision the pre-execution observation read. `moved_since_qualifying` in `crates/fiddle-runtime/src/orchestration.rs` calls it and stops the run when the two differ. MEASURED: `a_ticket_that_moves_after_it_is_qualified_opens_no_pull_request`.

**The gate grades its own rules, and no reader sees the grades.**

ARGUED, read off the source at `77b82f6`: `RuleState` has three variants: `Held`, `Failed` and `NotReached`, and the first two each carry an `EvidenceClass` of `Measured` or `Argued`. A rule decided from a field the tracker returned is therefore distinguishable from one decided by `ModelReview` reading the ticket text. `Refusal` carries that ledger.

ARGUED, read off the source at `77b82f6`: the ledger reaches no surface. `refusal_note` publishes the failed rule, what was found, the remedy and the quoted ticket text, and no more. Nothing outside `crates/fiddle-runtime/src/toil/qualify.rs` reads `Standing`, `rules_held` or `rules_not_reached`. So a person reading the comment on their own ticket is told which rule failed and is not told which of the other twelve were reached, nor on what class of evidence any of them stood.

**The gate and the implementer read one ticket text.** `toil::qualify` judged the summary followed by the description and `quoted_ticket` carried the description alone, so the step given the work was given less than the gate had judged, and every workflow-layer fixture set `summary: None` so no test could see it. Both now read `toil::ticket_text`, which joins whichever of the two carries content. MEASURED: `a_step_is_given_the_text_the_gate_judged_and_not_the_description_alone` in `crates/fiddle-runtime/tests/workflow_capability.rs` drives three work items — one carrying both, one whose summary carries the whole request and whose description carries nothing, and one carrying neither — and requires the quotation to be the gate's own text, the summary, and absent.

That claim is now scoped to the summary and the description. `toil::ticket_text` takes a third argument, the conversation. The gate passes the comments it admits, `quoted_ticket` passes none, and the section below records why and what it costs.

**The ambiguity review reads the conversation, and the implementer does not.**

`facts_of` in `crates/fiddle-cli/src/main.rs` carries `WorkItemState.comments` into `TicketFacts`, and `toil::deterministic` joins the comments it admits onto the summary and the description before it quotes the text the review reads. Before this the conversation was fetched, carried into the observation and dropped in `facts_of`, so a question the description left open could be closed only by editing the description, which is what the remedy for `ASKS_FOR_A_CHANGE` told the operator to do. ARGUED, read off the body of `fiddle-v6pu` and not off anything in this tree: the operator asked for the comment route on 2026-09-03, after a live run refused ISP-263 for that rule, because the rest of the automation on that site works by comment — the bot comments, a person replies, and the workflow re-runs and rebuilds its context from the ticket and the conversation.

The step the implementer runs is given no conversation. `quoted_ticket` in `crates/fiddle-runtime/src/capability/workflow.rs` passes an empty conversation, so it reads the summary and the description alone. Two reasons hold that, and one cost follows.

The review reads and cannot write. Its whole answer is a `Judgement` — a verdict, a span and a number — and `ModelReview` builds its agent with a preamble and no tool at all. The implementer runs through `attempt_briefed` under `Offer::Repair`, which grants `edit_file`, `write_file` and `run_check`, and `run_command` where the deployment declares commands. A comment is lower trust than a description, because commenting on an issue is a wider permission than editing one, so the wider surface is the one that is not given it.

`quoted_ticket` also holds no allowlist to apply. It takes a `WorkItemState` and nothing else, and the accounts a deployment authorized reach the gate through `Eligibility`, which the workflow capability is not given. Passing the conversation to the implementer would either widen that capability's inputs or drop the author rule below the gate, and the second is not a choice worth making.

ARGUED, read off the two call sites: the cost is that a ticket admitted because a comment decided the question hands the implementer a description that still leaves it open. No test holds this, and no bean records it yet.

**Whose comment counts is bounded by `[jira.decision] authorized`.**

Three rules were weighed. Every comment is context, whoever wrote it. Only a comment from an account in `[jira.decision] authorized` is context. Or every comment is context and each is attributed to its author in the quoted text, so the preamble can be told whose word to weigh.

The second is taken. `authorized_comments` in `crates/fiddle-runtime/src/toil/qualify.rs` keeps a comment when `Decider::JiraAccount(author)` is in `Eligibility.authorized_commenters`, which `toil_bounds` fills from `deciders`, the one function that builds that list from both decision tables. That list holds both channels, and the comparison is against the `Decider` value rather than against a string, so a numeric GitHub author id written in `[github.decision]` authorizes no comment however it is spelled — the namespace refusal ADR 081 records, reused here rather than restated. An absent `[jira.decision]` table therefore names nobody whose comment can count, so no comment is context and the gate reads what it read before. `a_comment_can_decide` asks the same question of the same list, and it is what the remedy branches on, so a deployment that named a GitHub decider and no Jira account is told about the description alone.

Three reasons hold it. A comment that moves the gate from refused to admitted decides something, and ADR 081 already names the accounts that may decide a question a run asked. Same act, same channel, same table: nothing new is configured, and `config check` already reports the accounts it holds.

Anyone who can comment on a project can comment on its tickets, and that set is wider than the set that may decide. On ISP-263 an automation bot has commented twice and moved the trigger label twice, minutes apart each time. Under the first rule that bot steers the gate.

The third rule rests on a model honouring an instruction. A preamble that names whose word to weigh is not a boundary: no test of it can assert more than that the sentence is in the preamble. A refusal has to be a comparison the gate makes. Attribution is separately unnecessary under the rule taken, because every comment in the quoted text is one the deployment authorized, so the model is never asked to weigh an author.

The author rule is not the whole rule, and the reason is not guessable from it. fiddle authors its Jira comments as the operator: `[jira] user` and `token` are the operator's own credential, so a refusal fiddle publishes reads back with the operator's `accountId` — the id they must write into `[jira.decision] authorized` for comment steering to work at all. Authorization by account therefore cannot tell fiddle's own writing from the operator's. So `authorized_comments` drops a comment `carries_a_marker_fiddle_writes` holds for, before it weighs the author. Two markers, because fiddle posts two kinds of comment: `fiddle-effect:` on every effect comment and `<!-- fiddle:decision` on every question. Without that, authorizing the operator would hand the review every refusal fiddle has already published on the ticket — which argues for the verdict that produced it, and, worse, puts a span inside the fence that `JUDGEMENT_QUOTES_THE_TICKET` accepts and the ticket does not carry. That rule exists so a judgement rests on the ticket, and this is what keeps it resting there.

The cost is stated rather than hidden. A deployment that has filled in no `[jira.decision]` table gets none of this, and an operator sees no comment reach the review until they name an account. That is the direction to fail in, and it is visible: `config check` reports the Jira table as `enforced-by-propose-change-and-by-the-toil-gate` and says in words that a comment from anybody else is not context the review reads. The refusal's remedy follows the same table. Where the deployment authorized an account the remedy names the comment route beside the description; where it authorized nobody it names the description alone, so it never sends an operator to a route their deployment does not have.


**`toil` is the selectable name, and `WORKFLOW` stays out of the registry.**

ARGUED, read off the source at `77b82f6`: `CAPABILITIES` holds six ids, and `fiddle_core::TOIL` is one of them. `WORKFLOW` is not, and ADR 074's reason still holds: every name in that array must be selectable on a command line, and a workflow needs a document. What changed is that `toil` names a document at a fixed path. `selected_workflow` maps `Selection::Toil` to `workflows/toil.toml` beside the deployment document, and refuses a file whose `stage` is not `toil`.

**A workflow earns typed outputs, and one step is read-only.**

ARGUED, read off the source at `77b82f6`: `StepOutputs` holds three values: a pull request number, a `Verdict` and a head sha. It is closed and typed. A document names none of the three, so the format gained no variable and no interpolation, which is what ADR 074 forbids. ADR 082 records the head sha half.

ARGUED, read off the source at `77b82f6`: `Step::Evaluate` runs the agent under `Offer::Judge`. That offer returns `READING` alone, so the judge is given `read_file`, `list_files` and `search_files` and is given neither `edit_file` nor `write_file` nor `run_check`. Its answer is a `Verdict` through `output_schema` with a required tool choice, so it is parsed and not read out of prose. A `Verdict::Rejected` breaks the step loop and the run reports `RunOutcome::Rejected`, which exits 12.

MEASURED through the binary: `a_workflow_the_judge_rejects_exits_twelve_and_a_workflow_it_accepts_does_not` in `crates/fiddle-acceptance/tests/capability_selection.rs` runs one document twice and changes only the verdict the gateway stub serves. The rejecting run exits 12 and the accepting run exits 0, so a build that exits 12 whatever the judge said fails the second half. The accepting run also carries the correlation marker its own summary names, and the rejecting run carries none.

**Scope is enforced in Rust, after the agent step and before any effect.**

ARGUED, read off the source at `77b82f6`: `Scope` carries `max_files_changed` and `max_diff_lines`. `WorkflowCapability::within_scope` measures the workspace after each agent step and refuses through `OutOfScope`. The document names no bound; `[orchestration.toil]` does, and an absent table resolves to 10 and 500 rather than to no bound.

MEASURED through the binary: `the_command_line_toil_route_enforces_the_bound_config_check_reports` in `crates/fiddle-acceptance/tests/capability_selection.rs`, where each bound refuses on its own and admits the same change when that one number is loosened. That lane names no effect step, so it measures the bound and not the ordering. The ordering is measured one level down, against the shipped document rather than through the binary: `a_change_beyond_the_bounds_stops_before_any_effect_and_each_bound_bites_on_its_own` and `a_change_inside_both_bounds_runs_to_the_effect_tail` in `crates/fiddle-runtime/tests/toil_document.rs` are the pair.

**The document has no `ask` step, and that is the requirement rather than an omission.**

ARGUED, read off the source at `77b82f6`: `Step` has five shapes: `Agent`, `Evaluate`, `Check`, `Effect` and `Commit`. It is a serde enum tagged by `kind` with `deny_unknown_fields`, so a document naming a sixth kind is refused when it loads. `WorkflowRefusal::Gated` separately refuses a document that names an effect whose minimum is `Human`.

ARGUED: a toil run therefore cannot suspend on a question by construction. Requirement 21 wants that: toil declines decision-heavy work at the gate instead of asking about it. The channel that asks a person a question belongs to `propose_change`, and ADR 081 records it.

## Consequences

**The epic's outcome, both halves, measured through the binary against loopback stubs, and two runs since observed against a real Jira site and a real model gateway.**

An eligible ticket produces one pull request and one link comment on the ticket. MEASURED: `an_eligible_ticket_produces_one_pull_request_and_one_jira_link` counts one pull request and one branch off the `gh` stand-in, one link comment off the tracker stub, and the four effect steps — `ensure_branch_published`, `ensure_pull_request`, `jira.pull_request_linked` and `jira.issue_transitioned` — in the order the shipped document names them. That document names seven steps, and these four are its effect steps. A second run over the same ticket adds neither, and three tests hold that for three different reasons. `a_second_run_over_the_same_ticket_adds_no_second_pull_request_and_no_second_link` pins the second run reading the correlation marker the first run recorded, deriving `complete`, and never executing the document at all; it pays for the eligibility review and for no agent turn. `a_retry_over_a_branch_this_invocation_already_published_reaches_the_effect_tail` removes that record first, so the run works the ticket again, rebuilds the commit the first run published and reaches all four effect steps, where the pull request step and the link step each recognise their own prior work. It used to refuse at the branch step instead, because the rerun's sha moved; `fiddle-buu6` fixed that and ADR 082 records how. `a_rerun_whose_branch_is_gone_finds_its_own_pull_request_and_its_own_link` removes the record and the remote branch, so the second run reaches all four effect steps, and the pull request step and the link step each name what the first run made. Inspect-before-write on those two effects is therefore measured.

An ineligible ticket is refused on its own issue with the reason on it, and the refusal is performed through the effect executor under an effect identity. MEASURED: `a_refused_ticket_is_told_why_on_its_own_issue`, named above, extracts the effect id from the marker inside the published comment and requires the run to print the same id. `a_deployment_that_denies_the_comment_effect_publishes_nothing_and_still_refuses` holds that deployment policy still governs the write, and `a_site_that_refuses_the_comment_still_refuses_the_ticket` holds that a tracker error does not turn the refusal into something else.

OBSERVED, on 2026-09-03, on the first of two runs: `fiddle run jira:ISP-263` against a real Atlassian site and the real gateway `bedrock/moonshotai.kimi-k2.5` at `https://litellm.firn.snplow.net/v1`. ISP-263 held the nine deterministic rules, the gateway answered, and the run was refused at `REVIEW_ANSWERED` and published that refusal on ISP-263 as comment `178879`, exit 2. The fault was this build's and not the ticket's: the gateway returned the answer inside a markdown fence, and `read` in `crates/fiddle-runtime/src/toil/review.rs` parsed a bare object only. So every eligible ticket was refused at the review whatever it said, and the refusal named a rule the model had not broken. That is what the sentence this paragraph used to carry was hiding.

MEASURED against the body that run recorded, which `tests/fixtures/gateway-real/review-answer.json` preserves verbatim: `unfenced` strips one leading and one trailing fence, with or without a language tag, and `read` refuses everything it still cannot parse with the message it carried before. `the_recorded_gateway_answer_is_read_through_the_fence_it_arrived_in` reads that recorded body, and `a_gateway_that_fences_its_answer_admits_the_ticket_it_answered_about` in `crates/fiddle-runtime/tests/toil_eligibility.rs` carries it through the gate to an admitted ticket. Reverting `read` to the bare parse reds both, and reds none of the lanes that require an unreadable answer to refuse. The preamble is unchanged and still asks for a single JSON object and nothing else, because a prompt cannot make a model comply.

OBSERVED, on 2026-09-03, on the second run: `fiddle run jira:ISP-263` against the same site and the real gateway `claude-sonnet-5` at `https://litellm.firn.snplow.net/v1`. This run held the nine deterministic rules, passed the review, and reached the agent step, which no run had reached against real infrastructure before. The agent read the file the ticket named, edited it, and ran the project's check, which exited 0. The run then discarded that work and reported `retryable — the attempt produced no report`, exit 11.
