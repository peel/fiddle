## Context

Requirement 21 of the product requirements document asks for a toil agent. That document is not in this tree; `docs/specs/` is gitignored and the bean body carries the contract. A labelled Jira ticket becomes one pull request, linked back onto the ticket, with no person in the loop.

ADR 074 had already settled the workflow format. A file is read and never evaluated, it holds no condition, and a capability that wants a condition belongs in Rust. `WorkflowCapability` existed under that rule, and nothing reached it from a command line.

Two questions were left. Where does the judgement "is this work fiddle takes on?" live. And what does the workflow document have to gain before it can carry the toil route at all.

This record grades each claim it makes. MEASURED means a test in this repository observes the behaviour. ARGUED means the claim is read off the source and no test fails if it is wrong. OBSERVED means a person ran it once against real infrastructure and recorded what happened, and no test in this repository reproduces that run. STILL NOT REACHED means no run has done the thing.

Every toil measurement below runs the compiled binary against a loopback model gateway, a loopback Jira server, a compiled stand-in for `gh`, and a local bare git repository as the remote. One toil run has since reached real infrastructure, and the Consequences record what it found: a real Jira site and a real model gateway on 2026-09-03, and no forge.

ARGUED, read off ADR 074 and off the source at `77b82f6`: the context above. No test asserts what ADR 074 settled, and none asserts that nothing reached `WorkflowCapability` from a command line before this milestone.

## Decision

**Eligibility is an outer Rust gate. It is not a step.**

ARGUED, read off the source at `77b82f6`: `toil::qualify` runs in `crates/fiddle-cli/src/main.rs`, in `qualified`, after `selected_workflow` loads the document and before the workflow runs. `RULES` holds the thirteen rule names the gate applies: twelve in `toil::qualify` and the thirteenth in `toil::recheck`. It answers `Qualification::Eligible` or `Qualification::Refused`, and a `Refusal` carries the rule that failed, what was found and the remedy that would change the answer. That order has a cost. ARGUED, read off the same source: a deployment whose toil document is malformed refuses before the ticket is qualified. So the ticket receives a document error rather than a refusal comment on its own issue, and the person who filed it is told nothing. No test drives a `jira:` toil run against a malformed document.

Three reasons hold the gate outside the document. That placement, all three reasons, and the three paragraphs that state them are ARGUED, read off the source at `77b82f6` and off ADR 074, except where a sentence names its own measurement. ADR 074 gives the first. Eligibility is nothing but conditions, and a condition in a file means the capability belongs in Rust.

The second is cost. An ineligible ticket must pay for no worktree, no forge client and no model call. Placing the judgement inside the document would spend all three to reach the step that declines the work. MEASURED: `a_refused_ticket_is_told_why_on_its_own_issue` in `crates/fiddle-acceptance/tests/toil.rs` counts zero model calls, zero pull requests and zero branches for a ticket without the trigger label, and the run exits 2.

That reason had a sibling cost this record did not name, and `fiddle-ihl1` removed it rather than recording it. `qualified` used to resolve `config.agent` and call `model_client`, which resolves the model credential, before it observed the ticket and before `toil::qualify` ran. So a deployment that configured no `[agent]` table answered a label-less ticket with `fiddle::config::capability_unconfigured`, naming a deployment fault the person who filed the ticket cannot act on, and never reaching the rule that would have told them what to do. `toil::qualify` now applies its twelve rules in two halves. `toil::deterministic` applies the nine that read the tracker's own fields and needs no model. `toil::review_of` applies the three the ambiguity review decides, and `qualified` resolves `[agent]` and the model credential only when the nine have held. `toil::qualify` is the two called in order, so no caller of the whole gate changed. Nine plus three is twelve, and `RULES` holds thirteen. The thirteenth is `TICKET_HELD_ITS_REVISION`, and it is in neither half. `toil::recheck` applies it against the revision the run observes, which the section below records. MEASURED through the binary: `a_ticket_the_deterministic_rules_refuse_is_refused_on_a_deployment_that_configured_no_model` drives a label-less ticket against a document with no `[agent]` table and requires the refusal, the comment on the ticket and exit 2 rather than the configuration error. Its pair, `a_ticket_the_deterministic_rules_admit_still_needs_the_agent_table`, drives an eligible ticket against the same document and requires the configuration error, so the first is about which rule failed and not about this build having stopped resolving `[agent]`.

The third is the refusal itself. A refusal is a write on the ticket, and the run that must not start cannot be the run that performs it. So the gate publishes the refusal, and the document never sees the ticket. ADR 084 records what that required of the effect executor.

**Each surface announces only the quotation it carries.**

A refusal carries at most one `Quoted`, and its `Source` says whether the text came off the ticket or off the model host's side of the review. The two surfaces therefore carry different quotations, deliberately. `refusal_note` publishes the ticket's own text back onto the ticket, because a reader of the issue can already read it, and never the host's message, because that is not text the issue holds and publishing it would disclose it rather than restate it. `not_work_this_build_takes_on` prints the host's message to the operator, who asked for this run and can act on what its gateway said, and prints no ticket prose, because the terminal is the surface the refusal keeps prose off.

The `found` sentence a rule builds is read by both surfaces, so it promises neither. Four rules used to write "is quoted below" into `found`. Three of them quote the ticket, which only the comment carries; the fourth is `REVIEW_ANSWERED`, whose quotation is the host's message, which neither surface carried. That fourth one reached ISP-263 on 2026-09-03 as comment `178879`, promising a quotation the comment was designed never to carry. `announcement_for` in `crates/fiddle-cli/src/main.rs` now pairs each `Source` with the sentence that announces it, and `announcing` renders that sentence and the text in one string, so a surface cannot announce a quotation without printing it.

MEASURED: `no_refusal_sentence_announces_a_quotation_the_surface_it_reaches_may_not_carry` in `crates/fiddle-runtime/tests/toil_eligibility.rs` drives every rule the gate has and requires no `found` and no remedy to promise a quotation, and requires four of those refusals to carry one, so the check is not passing over refusals with nothing to promise. `neither_surface_announces_a_quotation_it_does_not_print` in `crates/fiddle-cli/src/main.rs` drives a ticket-quoting refusal and a host-quoting refusal through `refusal_note` and `not_work_this_build_takes_on`, requires each surface to announce a quotation exactly when it prints one, requires an announcement to name the source its refusal rests on, and requires the two quotations to reach one surface each. `the_operators_line_carries_the_message_the_ticket_is_not_told` requires the divergence in both directions, and `a_refusal_note_leaves_out_what_the_model_host_said` still holds the host's message off the issue.

ARGUED, read off the source: the message the operator now reads is redacted and bounded. `ModelReview` holds the `Redaction` built from the model credential and puts the host's error through `Redaction::excerpt`, which replaces the credential and cuts at 240 characters, and withholds the message where the build holds no credential to redact with. Before this the rig error reached the refusal as its own `Display` and no surface printed it. No test in this tree asserts the redaction on this path.

**Both arms of the gate write on the ticket, and they say different things.**

An eligibility refusal is a write performed by the gate, because the run that must not start cannot be the run that performs it. A rejection is the other case: the run did start, the gate admitted the ticket, the agent changed the project and the evaluation declined the change. That write belongs to the run that did the work, so `WorkflowCapability::execute` performs it on the rejection arm through the same executor its documented effects go through, against the work item and the revision the `Eligible` it was qualified from carries. A run carrying no qualification names no work item and writes nothing.

The two texts must not be read for each other. A refusal opens `fiddle did not take` and a rejection opens `fiddle took ... on`, and the rejection says the change reached no branch and no pull request, because a reader who is told a change was made will otherwise look for one.

MEASURED through the binary: `a_rejected_run_says_so_on_the_ticket_it_came_from` in `crates/fiddle-acceptance/tests/toil.rs` drives an eligible ticket against a judge that rejects, reads the comment off the tracker stub and requires both findings in it, requires the effect identity in the run's receipt to be the identity the comment carries, and requires the refusal's own opening sentence to be present in a refusal comment and absent from this one. It counts zero branches off the remote and zero pull requests off the forge stub, so the sentence about them is true and not only published. `a_second_run_of_one_rejected_ticket_adds_no_second_comment` runs the same invocation twice, requires the second run to have executed the document again and paid for the whole route, and requires one comment. `a_site_that_refuses_the_comment_still_rejects_the_change_and_says_the_ticket_was_not_told` drives a site that answers 403 to the write, and requires the run to report the rejection anyway, to earn no effect receipt, and to record that the note reached no work item, because a rejection nobody received is not a rejection delivered. MEASURED at the capability: `a_rejected_run_writes_on_the_work_item_it_was_qualified_from_and_an_unqualified_one_writes_nowhere` in `crates/fiddle-runtime/tests/workflow_capability.rs` pairs the write with a run that concludes the same rejection carrying no qualification and writes nothing.

**A finding names the repository, and that is the deployment's own text.**

`refusal_note` publishes only text the issue already holds. A rejection's findings do not: they name paths, line numbers and symbols in a repository. The rule this record applies is not "publish only what the issue already holds" — that is the consequence, and not the reason. The reason is whose text it is. A model host's message is a third party's, obtained under this deployment's credential to that host, and putting it on the issue discloses it rather than restates it. A finding is fiddle's own sentence about its own change, and its subject is the repository the ticket's project maps to under `bounded_repositories`. The ticket names that repository and its reader is the person who asked for the change in it; on ISP-263 the conversation already discusses `metrics.go` by name. A tracker project and the repository a deployment maps it to are two surfaces of one organisation, so a path reaching the first from the second crosses no boundary that the mapping did not already cross. A deployment that maps a project to a repository whose readers are not the project's readers is misconfigured, and no rule about comment text repairs that.

ARGUED, read off the source: a finding names a site and does not quote it. `JUDGE_PREAMBLE` asks for "one sentence naming one thing you read", and the four findings the live run produced on ISP-263 name paths, line numbers and symbols and quote no source line. Nothing holds that bound. The model writes the finding, `Published::of` bounds its length and nothing bounds its content, so a judge that quoted a source file into a finding would put those lines on the ticket. That is the residual disclosure this decision accepts, and it is unmeasured.

**A qualification is rechecked against the revision the run observes.**

ARGUED, read off the source at `77b82f6`: `toil::recheck` compares the `fields.updated` the ticket was qualified at with the revision the pre-execution observation read. `moved_since_qualifying` in `crates/fiddle-runtime/src/orchestration.rs` calls it and stops the run when the two differ. MEASURED: `a_ticket_that_moves_after_it_is_qualified_opens_no_pull_request`.

**The gate grades its own rules, and no reader sees the grades.**

ARGUED, read off the source at `77b82f6`: `RuleState` has three variants: `Held`, `Failed` and `NotReached`, and the first two each carry an `EvidenceClass` of `Measured` or `Argued`. A rule decided from a field the tracker returned is therefore distinguishable from one decided by `ModelReview` reading the ticket text. `Refusal` carries that ledger.

ARGUED, read off the source at `77b82f6`: the ledger reaches no surface. `refusal_note` publishes the failed rule, what was found, the remedy and the quoted ticket text, and no more. Nothing outside `crates/fiddle-runtime/src/toil/qualify.rs` reads `Standing`, `rules_held` or `rules_not_reached`. So a person reading the comment on their own ticket is told which rule failed and is not told which of the other twelve were reached, nor on what class of evidence any of them stood.

**The gate and the implementer read one ticket text.** `toil::qualify` judged the summary followed by the description and `quoted_ticket` carried the description alone, so the step given the work was given less than the gate had judged, and every workflow-layer fixture set `summary: None` so no test could see it. Both now read `toil::ticket_text`, which joins whichever of the two carries content. MEASURED: `a_step_is_given_the_text_the_gate_judged_and_not_the_description_alone` in `crates/fiddle-runtime/tests/workflow_capability.rs` drives three work items — one carrying both, one whose summary carries the whole request and whose description carries nothing, and one carrying neither — and requires the quotation to be the gate's own text, the summary, and absent.

That claim now covers the conversation too. `toil::ticket_text` takes a third argument, the comments. The gate passes the comments it admits, and the section below records how the implementer comes to read the same ones.

**The ambiguity review and the implementer read one conversation, because they read one string.**

`facts_of` in `crates/fiddle-cli/src/main.rs` carries `WorkItemState.comments` into `TicketFacts`, and `toil::deterministic` joins the comments it admits onto the summary and the description before it quotes the text the review reads. **Whose comment counts is bounded by `[jira.decision] authorized`.**

Three rules were weighed. Every comment is context, whoever wrote it. Only a comment from an account in `[jira.decision] authorized` is context. Or every comment is context and each is attributed to its author in the quoted text, so the preamble can be told whose word to weigh.

The second is taken. `authorized_comments` in `crates/fiddle-runtime/src/toil/qualify.rs` keeps a comment when `Decider::JiraAccount(author)` is in `Eligibility.authorized_commenters`, which `toil_bounds` fills from `deciders`, the one function that builds that list from both decision tables. An absent `[jira.decision]` table therefore names nobody whose comment can count, so no comment is context and the gate reads what it read before. `a_comment_can_decide` asks the same question of the same list, and it is what the remedy branches on, so a deployment that named a GitHub decider and no Jira account is told about the description alone.

Three reasons hold it. A comment that moves the gate from refused to admitted decides something, and ADR 081 already names the accounts that may decide a question a run asked. Same act, same channel, same table: nothing new is configured, and `config check` already reports the accounts it holds.

Anyone who can comment on a project can comment on its tickets, and that set is wider than the set that may decide. On ISP-263 an automation bot has commented twice and moved the trigger label twice, minutes apart each time. Under the first rule that bot steers the gate.

The third rule rests on a model honouring an instruction. A preamble that names whose word to weigh is not a boundary: no test of it can assert more than that the sentence is in the preamble. A refusal has to be a comparison the gate makes. Attribution is separately unnecessary under the rule taken, because every comment in the quoted text is one the deployment authorized, so the model is never asked to weigh an author.

The author rule is not the whole rule, and the reason is not guessable from it. fiddle authors its Jira comments as the operator: `[jira] user` and `token` are the operator's own credential, so a refusal fiddle publishes reads back with the operator's `accountId` — the id they must write into `[jira.decision] authorized` for comment steering to work at all. Authorization by account therefore cannot tell fiddle's own writing from the operator's. So `authorized_comments` drops a comment `carries_a_marker_fiddle_writes` holds for, before it weighs the author. Two markers, because fiddle posts two kinds of comment: `fiddle-effect:` on every effect comment and `<!-- fiddle:decision` on every question. That rule exists so a judgement rests on the ticket, and this is what keeps it resting there.

The cost is stated rather than hidden. A deployment that has filled in no `[jira.decision]` table gets none of this, and an operator sees no comment reach the review until they name an account. **An attempt that changes nothing and names a question refuses the run with that question, and one that changes a file does not.**

`RepairReport` carries `stopped_by_this_question`. `WorkflowCapability::declined` reads it after the agent step and returns a finding only when the workspace is also unchanged; `stopped_by` writes that finding and `STOPPED_BY_A_QUESTION` opens it. **The field is what an attempt says, and the tree is what decides how the run reads it.**

A report that names a question over a tree it also changed is a substitution and not a decline. `declined` returns nothing in that case, the evaluation is asked, and the project is judged against the option the ticket named. `{project}: {invocation_ref}`, which read `identities: jira:ISP-263`. Neither named
the ticket a reader was looking for.

**The prefix is configuration and defaults to `fiddle`.** `[github] branch_prefix`
names it. `prefix_is_a_ref` refuses a value git could not hold — an empty segment,
a leading or trailing `/`, `..`, a segment ending `.lock`, anything outside ASCII
alphanumerics with `-`, `_` and `.` — and the refusal names the rule at the line
the operator wrote, through the same `deserialize_with` route `EnvRef` uses for a
credential. A mangled prefix would publish a branch git rejects at the push, after
the agent has done its work.

**Why the default is `fiddle` and not `toil`.** `scripts/live-github.sh` and
`scripts/verify-graphql-ready.sh` both set `REF_NAMESPACE="fiddle/"`, and
`docs/technical/effects-repository.md` states as a standing invariant that the
testbed holds no branch that is neither `main` nor under `fiddle/`, with its
cleanup closing pull requests and deleting branches by that prefix. A default of
`toil/` would put every toil branch outside the namespace that finds and removes
them, making each run permanent residue and the invariant false. An operator who
wants `toil/` can name it, and owns the cleanup consequence.

**The title carries the summary and the branch does not.** ADR 075 records what an
orphaned branch costs: a resumed run inspects for a branch that does not exist
under the new name, sees nothing, publishes a second, and the pull request pointing
at the first goes stale. A branch carrying a slug of the summary would move
whenever anyone reworded the ticket, which is a thing people do to tickets. The
branch therefore takes the ticket alone and no summary, and
`a_reworded_ticket_moves_the_title_and_never_the_branch` holds that, asserting
first that the two wordings differ so the case cannot pass on identical inputs.

**`branch_name` is unmoved.** publish, propose and cve still derive
`fiddle/{effect_id}`, so `the_branch_name_is_pinned_to_the_identity_derivation`
and the `starts_with("fiddle/")` assertions in
`crates/fiddle-acceptance/tests/exactly_once.rs` and
`crates/fiddle-acceptance/tests/human_direction.rs` are untouched. Only the toil
route names its branch this way.

**The title is refined from the observation and the branch is not.** The ticket key
is in the invocation, so the branch is known before the run observes anything. The
summary is not, so `execute` rebuilds `params.title` after `observing`.
`the_pull_request_title_carries_the_ticket_and_the_title_the_run_observed` asserts
the shape reaching the forge and asserts that the title the parameters carried
beforehand does not; deleting the refinement sends `fiddle: toil` and reds it.

## The pull request body carries a log of the work (2026-09-08)

`toil::body_carrying` appends a `<details><summary>Log</summary>` block to the body
the run already wrote. `WorkLog` comes from `of_transcript` when the run recorded
one and from `of_receipts` when it did not, and the block states which.

The point is inspecting how a run reached its result. The 111-turn run of 2026-09-05
spent 166 tool calls before its first edit, 143 of them `search_files`, 46
repeating a query already answered and 62 matching nothing. Only `args` carries
that, and `ToolReceipt` holds a tool name, one of four outcome words and a
duration. So a receipts-only log names counts and cannot name a repeat, and it says
so, naming `FIDDLE_TRANSCRIPT`. ADR 052 was reversed the same day so that the
richer source is the default one.

**Grouping comes before truncation.** Identical `(tool, args)` pairs collapse to
one row with a count, which both fits the budget and makes the repetition the
first thing a reader sees rather than 46 rows to scroll past. A body must fit the
forge's 65536 characters; when even the grouped table does not, rows are dropped
and the block states how many of how many, and
`a_log_too_large_for_the_body_drops_rows_and_names_how_many` holds that against
4000 distinct repeated calls.
