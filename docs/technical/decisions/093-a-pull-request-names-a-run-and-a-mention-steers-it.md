## Context

`fiddle-40l6`. Before this record a run on a pull request needed a Jira ticket. `fiddle run jira:ISP-263 --capability checks` found the ticket's pull request and worked it (ADR 090). A pull request that no ticket names could not be worked, and a person on the pull request could not start a run. ADR 090 named a `pr:` scheme and a mention trigger as the next slice.

The operator decided on 2026-10-08 that a pull request names a run by itself, and that a person starts the run by mentioning `@fiddle-ai` on it. fiddle writes as a GitHub App named `fiddle-ai`. The host workflow mints the App's installation token and passes it as `FIDDLE_GITHUB_TOKEN`, so fiddle holds no identity code beyond the account it writes as and the commit author. Creating the App needs an organisation admin and is not part of this record.

## Decision

**`pr:<owner>/<repo>#<n>` names a run. Only a person who speaks for the project, mentioning `@fiddle-ai` as a word in their own text, steers it. fiddle applies that rule itself, whatever started it.**

### The scheme and the record key

- `InvocationScheme::Pr` is spelled `pr`. `PullRequestRef` parses its value: owner and repository of ASCII letters, digits, `-`, `_` and `.`, and a positive decimal number with no leading zero. A value of any other shape, or a number above the largest `u64`, is `InvocationRefError::MalformedPullRequest`, which names the form `pr:<owner>/<repo>#<number>`. `pr:` with no value is `InvocationRefError::EmptyValue`, as for every scheme, and its advice is written in the `pr:` shape. `InvocationRef::pull_request` answers the `PullRequestRef` of a `pr:` reference and nothing for any other scheme, and `PullRequestRef::full_name` is `<owner>/<repo>`. Every other scheme keeps the value rule of ADR 011.
- `InvocationRef::record_key` is `<owner>+<repo>+<n>`, and `InvocationRef::slug` is `pr-<owner>+<repo>+<n>`. A `pr:` run that reaches the end of its steps and is not rejected writes its change record, through `record_change_set`, to `<[stub] root>/changes/<owner>+<repo>+<n>.json`. `+` is in no GitHub name and `-` is in many, so two pull requests never share a key (ADR 011, amended).
- A record fiddle wrote does not stop a `pr:` run. A `pr:` reference is `Addressed::NoWorkItem`: a pull request is the direction's thread, not a work item. A marker over a reference that addresses no work item is not a completion, as `a_marker_over_a_trackerless_reference_is_not_a_completion` in `crates/fiddle-core/src/assessment.rs` holds, so a second run in the same `[stub] root` reads the pull request again. What decides whether there is work is the answer on the pull request: each run answers only the mentions not yet answered. To run a mention again, a person deletes fiddle's answer or posts a new mention. A record fiddle cannot read is different: `StubChangePort` reads it as `Observation::Unavailable`, and `assess` turns that into `CapabilityAssessment::Blocked` for any reference, so a run over it is blocked until the record is removed.
- `PULL_REQUEST` is the capability id `pull_request`, and `CAPABILITIES` holds eight ids with it. `pr:` with no `--capability` selects `Selection::PullRequest`. `workflow_of` maps it to `PULL_REQUEST_DOCUMENT`, `workflows/pull_request.toml`, under `PULL_REQUEST_STAGE`, read beside the deployment document. Its steps are steer, checks, agent, evaluate, commit and `ensure_branch_published`. There is no ticket gate, no tracker table and no `ensure_pull_request`: the pull request exists.
- `--capability toil` over a `pr:` reference exits 2 with `ToilOverAPullRequest`, which `toil_works_no_pull_request` returns, in `run` and in `inspect`, before any port or the forge. Toil works a ticket and would open a second pull request. `--capability checks` over a `pr:` reference runs (ADR 022, amended).

### The read and its refusals

Before the run, `served_pull_request` compares the repository the reference names, its `PullRequestRef::full_name`, with `[github] repo`, ignoring ASCII case, because GitHub names do. A different repository is `ForeignPullRequest`, a configuration error, exit 2, before any request.

Then `open_on_the_served_repository` reads `GET /repos/{repo}/pulls/{n}` once with `read_pull_request`, into `PullRequestFacts`. `PullRequestFacts::from_json` refuses a response without a number, a state, a head ref, a head sha or a base ref as malformed, and reads a deleted head repository as none. `open_on_the_served_repository` refuses with `PullRequestRefused`, exit 2, and a reason that names the pull request:

- a closed or merged pull request: nothing to do;
- a head branch in another repository: naming the fork, because fiddle cannot push to it.

An unreadable pull request is `PullRequestUnread`, a forge failure, exit 11, retryable.

The run's branch is the head ref and its base the base ref. The push never forces, so a branch that moved during the run is refused and the next mention starts again.

### The mention rule

On a `pr:` run, `directing` keeps a comment or review only when two things hold.

- `mentions` finds `@fiddle-ai`, the handle `MENTION` names, as a word: not inside a longer word, an address or another handle, and ASCII case aside. `without_code_or_quotes` first leaves out inline code spans, fenced blocks and quoted lines. A mention someone quotes or shows as code asks for nothing.
- `speaks` holds for its author: `entitled`, so OWNER, MEMBER or COLLABORATOR as `ENTITLED` lists them, and not a bot. `AuthorKind` reads who wrote it from the account type, the same way for comments and reviews. `is_a_bot` is true for a `Bot` account whatever its association. A person posting through an App is `PersonThroughAnApp`: `is_automated` but not `is_a_bot`, so the person speaks.

A stranger's mention steers nothing, and a member's comment without the mention steers nothing. A bot never steers, even as a member and even when it mentions the handle. The CVE path asks the same question through `speaks` and `cited` in `CveMitigate::direction`, so one rule says who speaks for the project on every direction path.

`with_the_bots_they_cite` adds a bot's comment or review that a kept mention names by its login, such as `claude[bot]` in "do Claude's comments 1 and 2". `cited` decides the naming, and `is_the_handle` keeps out the login that is the handle itself, `fiddle-ai` or `fiddle-ai[bot]`. Such a comment is quoted as context, never followed as work, and it steers nothing by itself.

No bot is ever marked answered. A bot's comment that a later mention names still reaches that later run.

### The account fiddle writes as, and the answer

`[github] account`, for example `fiddle-ai[bot]`, is optional. An App's comment carries the association `NONE`. `unanswered` and `already_answered` trust an answered marker only in a `trusted` comment, which is an entitled author's or, through `written_by` and `is_account`, the configured account's. The login is matched ignoring ASCII case, and a login that only starts like the account is not it. The account's comments and reviews are never direction, and its replies are fiddle's own.

The answer effect, `pull_request_answered`, observes its own reply after it posts it. `AnswerPullRequest` takes the run's account through `written_as`. It trusts a reply the configured account wrote, as `unanswered` does. Without `account` the App's reply is never observed, the first run does not exit 0, and the next run answers the same mention again. When `account` is absent the rule before this record holds.

### The author

`[github.author]`, a table of `name` and `email`, is optional. `Author` reads it, refusing an empty name, an address without `@` and a key it does not read. `Author::resolved` turns it into `CommitAuthor`, and `committer` makes it the author and committer of every commit fiddle makes. Absent, commits carry `FIDDLE_NAME` and `FIDDLE_EMAIL`, `fiddle <fiddle@invalid>`, as before. `HOOKS_DISABLED` holds in either case: a hook on the machine does not refuse fiddle's commit. For the App the author is `fiddle-ai[bot]` and `<app-user-id>+fiddle-ai[bot]@users.noreply.github.com`.

### The trigger

`docs/technical/host-workflow-fiddle-ai.yml` is a template for the target repository's `.github/workflows/`. It runs on `issue_comment` created on a pull request and `pull_request_review` submitted. It does not run on `pull_request_review_comment`: the steer step reads the conversation and the reviews, and no inline comment on a line of the diff, so a mention there would start a run that finds nothing to answer. Its job `if` requires the text to mention `@fiddle-ai`, the author association to be OWNER, MEMBER or COLLABORATOR, and the sender not to be a `Bot`. The job, not the workflow, holds one concurrency group per pull request, with `cancel-in-progress: false`, so a later run never cancels a running one between its push and its answer. Only a run that passed the `if` enters the group. At workflow level every comment and review the workflow receives would enter it: one without the mention, and fiddle's own answer posted with the App token. GitHub keeps one waiting run per group and replaces it with the newest, so a skipped event would replace a waiting mention and the mention would be lost. Its own `GITHUB_TOKEN` reads contents only. It checks out the default branch by name, `ref: ${{ github.event.repository.default_branch }}`, with `persist-credentials: false`. Without `ref`, a review event checks out the pull request's merge ref, so the pull request would supply the deployment document, the workflow documents and the prompts fiddle reads, and a conflicting pull request would fail the checkout. It mints the installation token with `actions/create-github-app-token`, verifies the fiddle release against a pinned digest, and runs `fiddle run "pr:${{ github.repository }}#<n>"`. Its header lists the permissions the App needs, `contents: write`, `pull-requests: write`, `issues: write`, `checks: read` and `actions: read`, and the two events the workflow runs on; the App subscribes to no event, because the workflow receives them from the repository.

**fiddle re-applies its own rule, and the `if` is only a filter.** The `if` cannot see code spans, fences or quotes, and GitHub's `contains` matches `@fiddle-ai` inside a longer handle. A run that the `if` lets through reads every comment and review again under the mention rule above. So a wrong or edited `if` can start a run it should not, and that run answers only the mentions fiddle's own rule admits. It cannot widen who steers. `scripts/test-host-workflow-fiddle-ai.sh` holds the template in the gate: the template's bytes must equal the reviewed copy's (its sha256 is held beside it); any edit to the template, a comment included, fails the gate until the held sha256 is changed.

`scripts/local-toil-rerun.sh` decides nothing itself. It runs `fiddle inspect <ref> --config <document> --json` and prints fiddle's change observation and assessment as `jq -c` prints them from fiddle's answer, with one sentence restating whether fiddle reports the change record available or unavailable, and fiddle's reason. When fiddle exits non-zero, as it does for a malformed reference, the script prints fiddle's error as it is and exits with fiddle's code; when fiddle cannot be run or answers in a shape the script does not read, it exits 2. Each of `--config`, `--ref` and `--fiddle` given with no value refuses with exit 2 and names the flag. `--forget` removes only the record fiddle named, `stub:changes/<name>.json` with a name of `[A-Za-z0-9._:+-]` ending in `.json`, under the `[stub] root` `fiddle config check --json` reports. It refuses a root that is not absolute or holds a C0, DEL or C1 control character, because the shell cannot name such a path safely: fiddle reports the record's source without its root, so the script cannot check the root against it. It removes the record only when it is a regular file, a symlink or an empty directory and checks that the path is gone; anything else it leaves, and exits 2. It prints the run for the operator to type and does not run it.

## Consequences

- A pull request that no ticket names can be worked, and the person who asks is on the pull request.
- A `pr:` run reads the pull request once, before its first step. A refused pull request costs nothing more.
- Two mention runs on one pull request queue: a later mention waits for the running one. Only runs that passed the `if` queue, so a skipped event cannot replace a waiting mention. GitHub keeps one waiting run per group, so a third mention replaces the second while the first runs. The second mention is not lost: the run that follows answers every mention not yet answered.
- A deployment with an App must set `[github] account`, or every run answers every mention again. `fiddle config check` does not print `account` or `author`, so a missing `account` shows only as a second answer.
- `jira:` runs keep their direction rule. The mention rule applies to `pr:` runs only.
